How this works

DOCX → PDF

The file is rendered in-browser by docx-preview, which parses document.xml, styles.xml, theme1.xml, and the header/footer parts. Before rendering, the page swaps Calibri for Carlito and Cambria for Caladea — free fonts engineered to match the original character widths and line heights exactly, so the rendered content has the same page count as Word would produce.

The rendered HTML is paginated by html2pdf.js at the source DOCX's own page dimensions, with page-break rules applied to paragraphs, table rows, and list items so breaks fall in the gaps rather than mid-content. The browser print engine is never invoked, so no URL, date, or page-number captions are injected.

PDF → DOCX

The file is parsed by PDF.js, which returns positioned text fragments per page. Fragments are grouped into lines by Y-coordinate, lines into paragraphs by vertical gap, and each paragraph is classified as heading or body by comparing its font size to the document's median.

The result is assembled into document.xml, packaged with the minimum OOXML scaffolding, and zipped into a real .docx you can open in Word. Best for prose-heavy documents — diagrams and multi-column layouts may not survive the round-trip.
