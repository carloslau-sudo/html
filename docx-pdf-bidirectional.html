How this works

DOCX → PDF. The file is rendered in-browser by docx-preview, a proper OOXML renderer that parses document.xml, styles.xml, theme1.xml, and the header/footer parts to produce a layout that matches what Word renders — fonts, colors, table cell shading, Title and Subtitle styles, page headers and footers, lists, and inline run formatting all flow through. The resulting HTML and scoped CSS are handed to your browser's print engine, which subsets fonts and applies standard compression. The output is typically 30–60% smaller than Word's own export, with full visual fidelity.

PDF → DOCX. The file is parsed by PDF.js, which returns positioned text fragments per page. Fragments are grouped into lines by Y-coordinate, lines into paragraphs by vertical gap, and each paragraph is classified as a heading or body text by comparing its font size to the document's median. The result is assembled into document.xml, packaged with the minimum OOXML scaffolding, and zipped into a real .docx you can open in Word.

Caveats for PDF → DOCX. The default text-extraction mode works well for prose-heavy documents (reports, memos, runbooks). It struggles with diagrams, flowcharts, multi-column layouts, complex tables, and footnotes — because those rely on vector graphics or non-linear positioning that the text layer alone can't reconstruct. For documents like that, switch the Output setting to Page images: each page is rendered to a PNG and embedded in the DOCX, preserving the diagram exactly at the cost of making the text non-selectable. Image-only (scanned) PDFs have no extractable text and will produce an empty document in text mode — page-images mode is the only useful option for those.
